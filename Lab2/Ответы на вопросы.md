2. Аномальный bss у core.o - 50000 байт, хотя сам файл весит около 6 КБ. Это одна статическая переменная large_buffer, скорее всего что-то вроде static char large_buffer[50000] без инициализации

На диске содержимое .bss не хранится вообще. У секции тип NOBITS, в файле записан только её размер, а память выделяется и заполняется нулями уже при загрузке программы. Это видно по смещениям: .bss и .rodata начинаются с одного и того же смещения 0x1048, то есть .bss в файле места не занимает
```text
[A1@A1-pc Lab2]$ readelf -S -W core.o | grep -E 'bss|rodata'
  [ 4] .bss              NOBITS          0000000000000000 001048 00c350 00  WA  0   0 32
  [ 5] .rodata           PROGBITS        0000000000000000 001048 00004c 00   A  0   0 16
```

5. Общие имена: system_mode (core.o, legacy.o, hotfix.o), print_status (core.o, main.o), apply_hotfix (hotfix.o, main.o). print_status и apply_hotfix - это нормально, в одном файле функция определена, в другом просто вызывается. А вот system_mode определена сразу в трёх файлах

6.
```text
[A1@A1-pc Lab2]$ readelf -s core.o legacy.o hotfix.o | grep 'system_mode'
     7: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    3 system_mode
     6: 0000000000000004     4 OBJECT  GLOBAL DEFAULT  COM system_mode
     3: 0000000000000001     4 OBJECT  GLOBAL DEFAULT  COM system_mode
```
system_mode: в core.o тип D, Ndx 3 (.data); в legacy.o тип C, Ndx COM; в hotfix.o тип C, Ndx COM. У COMMON символов в Value хранится выравнивание - 4 у legacy.o и 1 у hotfix.o

print_status: в core.o тип T, Ndx 1 (.text); в main.o тип U, Ndx UND

apply_hotfix: в hotfix.o тип T, Ndx 1 (.text); в main.o тип U, Ndx UND

7. В core.o system_mode инициализированная переменная на 4 байта (в .data лежит 01 00 00 00), читается через mov в 32-битный регистр и печатается через %d. То есть там скорее всего int system_mode = 1. В legacy.o это COMMON на 4 байта с выравниванием 4, и туда пишется число 42 (movl $0x2a), значит int system_mode без инициализации. А в hotfix.c это char[4].

Получается, что каждый модуль думает, что у него своя переменная, а после линковки это одна и та же память, причём с разными типами. Хотфикс пишет туда байты 'A' 'B' 'C' '\0', а core потом читает это как int.


## Этап 3

```text
[A1@A1-pc Lab2]$ gcc -fcommon core.o legacy.o hotfix.o main.o -o app
[A1@A1-pc Lab2]$ ./app
System Initialized v1.0, Mode: 1
System Initialized v1.0, Mode: 4407873
```

8. Ни ошибки, ни предупреждения не было. COMMON символ это слабое определение, и линковщик по правилам просто склеивает все такие символы с одним сильным определением из core.o, для него это нормальная ситуация. Ошибка была бы только при двух сильных определениях. К тому же линковщик вообще не знает типов, он видит только имя, размер и выравнивание, а размер везде 4 байта.

Результат при этом сломан: 4407873 = 0x434241, это и есть "ABC", прочитанное как int.


## Этап 4

```text
[A1@A1-pc Lab2]$ nm app | grep system_mode
0000000000004040 D system_mode
```

9. system_mode попала в .data. Сильное (инициализированное) определение из core.o всегда побеждает COMMON символы, а раз у переменной есть начальное значение 1, её надо хранить в .data. Ссылки из legacy.o и hotfix.o просто направляются на неё.

10. Команда из задания у меня собралась без ошибок
```text
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix.o legacy.o core.o -o app_better
[A1@A1-pc Lab2]$ echo $?
0
```
Это потому что -fno-common флаг компилятора, а тут на вход идут уже скомпилированные .o, где system_mode уже лежит как COMMON. Поэтому hotfix.c был пересобран с этим флагом, и тогда ошибка появляется
```text
[A1@A1-pc Lab2]$ gcc -c -fno-common hotfix.c -o hotfix_nocommon.o
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix_nocommon.o legacy.o core.o -o app_better
/usr/bin/ld: warning: alignment 1 of normal symbol `system_mode' in hotfix_nocommon.o is smaller than 4 used by the common definition in legacy.o
/usr/bin/ld: warning: NOTE: alignment discrepancies can cause real problems.  Investigation is advised.
/usr/bin/ld: core.o:(.data+0x0): multiple definition of `system_mode'; hotfix_nocommon.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status
```
Исправить можно, если в hotfix.c заменить определение на объявление через extern (файл hotfix_fixed.c), тогда hotfix будет использовать переменную из core.o
```c
extern char system_mode[4];
```
```text
[A1@A1-pc Lab2]$ gcc -c -fno-common hotfix_fixed.c -o hotfix_fixed.o
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix_fixed.o legacy.o core.o -o app_fixed
[A1@A1-pc Lab2]$ echo $?
0
```
Но проблема с разными типами при этом никуда не делась, программа всё так же выводит Mode: 4407873
