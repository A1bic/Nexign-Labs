5. Общие имена (встречаются более чем в одном файле):
- `system_mode` - в `core.o`, `legacy.o`, `hotfix.o`. Это главная проблема: переменная **определена** сразу в трёх модулях.
- `print_status` - определена в `core.o`, используется в `main.o`.
- `apply_hotfix` - определена в `hotfix.o`, используется в `main.o`.

`print_status` и `apply_hotfix` - нормальная ситуация (один модуль определяет, другой ссылается). А вот `system_mode` - конфликт.

6. Разбор по каждому общему имени (`readelf -s`):

| Имя | Файл | Тип в `nm` | Ndx | Размер | Комментарий |
|---|---|---|---|---|---|
| `system_mode` | `core.o` | `D` | 3 (`.data`) | 4 | сильное определение, инициализированное |
| `system_mode` | `legacy.o` | `C` | `COM` | 4 | COMMON, выравнивание 4 |
| `system_mode` | `hotfix.o` | `C` | `COM` | 4 | COMMON, выравнивание 1 |
| `print_status` | `core.o` | `T` | 1 (`.text`) | 52 | функция |
| `print_status` | `main.o` | `U` | `UND` | - | внешняя ссылка |
| `apply_hotfix` | `hotfix.o` | `T` | 1 (`.text`) | 39 | функция |
| `apply_hotfix` | `main.o` | `U` | `UND` | - | внешняя ссылка |

Вывод `readelf -s` для `system_mode`:
```text
[A1@A1-pc Lab2]$ readelf -s core.o legacy.o hotfix.o | grep 'system_mode'
     7: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    3 system_mode
     6: 0000000000000004     4 OBJECT  GLOBAL DEFAULT  COM system_mode
     3: 0000000000000001     4 OBJECT  GLOBAL DEFAULT  COM system_mode
```
У COMMON-символов в поле Value хранится не адрес, а требуемое выравнивание: 4 у `legacy.o` и 1 у `hotfix.o`.

7. Что можно понять без исходников:
- **`core.o`**: `system_mode` - инициализированная глобальная переменная размером 4 байта с выравниванием 4. В `.data` по смещению 0 лежит `01 00 00 00`. В `print_status` она читается 32-битной инструкцией `mov 0x0(%rip),%edx` и передаётся в `printf` под `%d` (`"%s, Mode: %d\n"`). То есть в исходнике было примерно `int system_mode = 1;`.
- **`legacy.o`**: COMMON-символ размером 4 и с выравниванием 4, и в `apply_legacy_patch` в него пишется 32-битное число: `movl $0x2a, system_mode` (42). Значит там `int system_mode;` без инициализатора.
- **`hotfix.c`**: `char system_mode[4];` - тоже COMMON на 4 байта, но с выравниванием 1, потому что это массив `char`.

Конфликт: три модуля думают, что каждый из них владеет **своей** переменной `system_mode`, а на деле после компоновки это будет **одна** и та же ячейка памяти. Причём с разными типами: `core` и `legacy` считают, что это `int`, а `hotfix` - что это `char[4]`. Хотфикс записывает туда байты `'A' 'B' 'C' '\0'`, а `core` потом прочитает их как `int` и получит мусор. Это нарушение правила одного определения (ODR), которое компилятор не видит, т.к. компилирует каждый файл отдельно.


## Этап 3

```text
[A1@A1-pc Lab2]$ gcc -fcommon core.o legacy.o hotfix.o main.o -o app
[A1@A1-pc Lab2]$ echo $?
0
```

8. Компоновщик не выдал ни ошибки, ни предупреждения - сборка молча прошла.

Почему так:
- COMMON-символ (`C`) - это "предварительное" (tentative) определение. Компоновщик по правилам старого C обязан слить все COMMON-символы с одним именем в одну переменную, а если есть сильное определение (`D` из `core.o`), то все COMMON-символы просто "привязываются" к нему. Для компоновщика это штатная ситуация, а не ошибка. Ошибка `multiple definition` возникает только когда сильных определений два и больше.
- Компоновщик вообще ничего не знает о типах в C. В ELF-символе есть только имя, размер, выравнивание и секция. `int` на 4 байта и `char[4]` на 4 байта для него неотличимы

```text
[A1@A1-pc Lab2]$ nm app | grep system_mode

[A1@A1-pc Lab2]$ readelf -S -W app | grep -E '\.data |\.bss '
  [26] .data             PROGBITS        0000000000004020 003020 000fe8 00  WA  0   0 32
  [27] .bss              NOBITS          0000000000005020 004008 00c378 00  WA  0   0 32
```

9. `system_mode` оказался в `.data` (тип `D`, адрес `0x4040` попадает в диапазон `.data` `0x4020..0x5008`).

Почему: правило разрешения символов - сильное определение (инициализированная глобальная переменная из `core.o`) всегда побеждает COMMON-символы. Раз в `core.o` переменная инициализирована значением `1`, это значение надо где-то хранить, поэтому она остаётся в `.data`. COMMON-символы из `legacy.o` и `hotfix.o` никакой памяти не получают - их ссылки просто перенаправлены на определение из `core.o`. В `.bss` переменная попала бы только если бы все определения были COMMON (тогда компоновщик выделил бы место по наибольшему размеру).

---

Пересборка с `-fno-common`:
```text
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix.o legacy.o core.o -o app_better
[A1@A1-pc Lab2]$ echo $?
0
[A1@A1-pc Lab2]$ nm app_better | grep system_mode
0000000000004040 D system_mode
```

10. В моём случае эта команда **прошла без ошибок**. Причина в том, что `-fno-common` - это флаг **компилятора**, а не компоновщика: он влияет на то, как компилятор генерирует символы для неинициализированных глобальных переменных. Здесь `gcc` получает только готовые `.o`, компиляции не происходит, поэтому флаг ничего не меняет - в `hotfix.o` и `legacy.o` уже записаны COMMON-символы.

Чтобы флаг подействовал, надо перекомпилировать `hotfix.c` с `-fno-common`. Тогда `system_mode` в `hotfix.o` становится обычным сильным определением в `.bss` (`B`) вместо `C`:
```text
[A1@A1-pc Lab2]$ gcc -c -fno-common hotfix.c -o hotfix_nocommon.o
[A1@A1-pc Lab2]$ nm hotfix_nocommon.o
0000000000000000 T apply_hotfix
0000000000000000 B system_mode
```
И вот теперь компоновщик выдаёт ошибку:
```text
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix_nocommon.o legacy.o core.o -o app_better
/usr/bin/ld: warning: alignment 1 of normal symbol `system_mode' in hotfix_nocommon.o is smaller than 4 used by the common definition in legacy.o
/usr/bin/ld: warning: NOTE: alignment discrepancies can cause real problems.  Investigation is advised.
/usr/bin/ld: core.o:(.data+0x0): multiple definition of `system_mode'; hotfix_nocommon.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status
```
Два сильных определения (`B` в `hotfix` и `D` в `core`) - `multiple definition`.

Как исправить `hotfix.c`, не меняя имён: превратить определение в **объявление** с помощью `extern`. Тогда `hotfix.o` не будет создавать свою переменную, а будет ссылаться на ту, что определена в `core.o` (`hotfix_fixed.c`):
```c
extern char system_mode[4];

void apply_hotfix(void) {
  system_mode[0] = 'A';
  system_mode[1] = 'B';
  system_mode[2] = 'C';
  system_mode[3] = '\0';
}
```
```text
[A1@A1-pc Lab2]$ gcc -c -fno-common hotfix_fixed.c -o hotfix_fixed.o
[A1@A1-pc Lab2]$ nm hotfix_fixed.o
0000000000000000 T apply_hotfix
                 U system_mode
[A1@A1-pc Lab2]$ gcc -fno-common main.o hotfix_fixed.o legacy.o core.o -o app_fixed
[A1@A1-pc Lab2]$ echo $?
0
```

Важно: это исправляет только ошибку компоновки. Логическая проблема с разными типами остаётся - `app_fixed` всё так же печатает `Mode: 4407873`, т.к. хотфикс пишет символы в то, что `core` считает `int`. По-хорошему нужен общий заголовочный файл с одним объявлением `extern int system_mode;` (или `extern char system_mode[4];`), который подключают все модули, - тогда расхождение типов поймал бы компилятор.
